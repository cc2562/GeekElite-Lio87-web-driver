## 宏读取报错「宏存储 used_end 无效：26」定位分析（仅分析，未改代码）

- 报错位置：`src/macro.ts:63`（`macroUsedEnd`，阈值 `MACRO_HEADER_MIN_SIZE = 0x24`），
  由 `src/device.ts:141` 第一次 56 字节 0x14 探测后立即调用。
- 触发路径：连接 → `App.readMacros()`（`App.tsx:213`）→ `readMacroStorage` →
  `readMacroStorageUnlocked` 读 offset 0/len 56 → magic `AA 55` 通过 → bytes[2..3] = `1A 00` = 26 → 抛错。
- 结论：26 在代码假设的布局下**结构性不可能合法**（Header 至少 0x24=36 字节；10 个 entry 各 4 字节时
  最小合法 used_end 实为 0x4C=76）。因此拒绝本身没错，问题在「拿到的字节 ≠ 模型假设的 header」。
- 两个候选家族：① 读取层面（基址/分块语义/未初始化扇区）；② Header 布局或字段语义与逆向假设不同
  （字段偏移、大小端、used_end 语义）。区分方法：首个 56 字节已同时包含 Header 和 M1 marker（0x24 处），
  一次 hexdump + marker 扫描即可判定。
- 发现的次要缺陷：`App.tsx:216-223` 的 catch 会 `setMacroRaw(null)`，把已收到的 56 字节丢弃，
  导致 UI 提示「仍可导出当前数据」与实际不符，也让这个 bug 一直缺少原始证据。
- 修复方向（待确认）：诊断优先（错误对象携带 raw + hexdump + 候选布局报告、保留导出入口）；
  布局改为按证据探测（magic/count=10/offsets 单调/每 entry `35 00`/末尾 == used_end 全部自洽才接受）；
  写路径保持在布局未确认时硬拒绝；禁止用「放宽阈值」的方式绕过。

## 根因确认并修复：不是数据坏了，是结构读错了（用户提供实机样本）

实机 56 字节开头 `AA 55 1A 00 01 00 … 12 00 01 00 35 00 66 03 0A 04` 的真相：

- entry 头顺序是 `<action_count:uint16> 35 00`，此前写反成 `35 00 <action_count>`，entry 起点错开 2 字节；
- Header `0x04` 是**当前序列化的 entry 数量**（1–10），不是固定 10；offset table 长度 = entry_count × 2；
- 于是 `offsets[0] = 0x12`（0x10+2）、`0x12+4+1×4 = 0x1A = used_end`，26 完全合法。

- `src/macro.ts` 重写常量与解析：`MACRO_HEADER_FIXED_SIZE=0x10`、`MACRO_ENTRY_MARKER`、
  `MACRO_MIN_STORAGE_SIZE=0x16`、去掉 `MACRO_HEADER_MIN_SIZE`；`MacroStorage` 增加 `entryCount`；
  `parseMacroStorage` 按 entry_count 动态建 offset table 并逐 entry 校验 (action_count@+0, marker@+2)；
